# Data Model: Imagine Command

**Feature**: Imagine Command for Solution Design  
**Date**: 2026-02-03  
**Purpose**: Define data structures and entities for solution design generation

---

## Overview

The imagine command processes artifacts and generates solution design documents. This data model defines the structure of inputs (artifacts), processing state (progress tracking), user interactions (clarifications), and outputs (solution design document).

**Key Principle**: All data is file-based and human-readable (markdown, JSON). No database or persistent storage beyond the file system.

---

## 1. Solution Design Document

**Location**: `./solution-design.md` (project root)  
**Format**: Markdown with YAML frontmatter  
**Lifecycle**: Generated by `/speckit.imagine`, versioned on subsequent runs (v2, v3...)

### Structure

```yaml
---
title: string                 # Solution name extracted from artifacts
created: date                 # YYYY-MM-DD format
version: string               # v1, v2, v3... (auto-incremented)
artifact_count: integer       # Number of artifacts processed
last_updated: date            # YYYY-MM-DD format
---
```

```markdown
# [Title] - Solution Design

## 1. Executive Summary
- 2-4 paragraphs
- Business need, solution approach, capabilities, stakeholders

## 2. Architecture Overview

### 2.1 System Context (C4 Context Diagram)
- Mermaid C4Context code block
- Description of actors and system boundary

### 2.2 Container Architecture (C4 Container Diagram)
- Mermaid C4Container code block
- Description of components and technologies

## 3. Features
- Array of Feature entities (see below)

## 4. Assumptions & Open Questions (optional)
- Only if clarifications were insufficient

## 5. Next Steps
- Recommendations for detailed specification
```

### Validation Rules

1. **Frontmatter**: Must be valid YAML, title and created date required
2. **Summary**: 2-4 paragraphs (300-600 words)
3. **Diagrams**: Both C4Context and C4Container must pass mermaid-diagram-validator
4. **Features**: Minimum 1 feature, each must have source reference
5. **Versioning**: Filename increment logic (solution-design.md → solution-design-v2.md)

## 2. Feature Entity

**Definition**: High-level capability description extracted from artifacts or clarifications

### Attributes

| Attribute | Type | Required | Description |
|-----------|------|----------|-------------|
| `title` | string | Yes | Feature name (noun phrase, e.g., "User Authentication") |
| `description` | string | Yes | User value statement, 1-3 sentences, max 300 chars |
| `source_type` | enum | Yes | "artifact" or "clarification" (mutually exclusive) |
| `source_reference` | string | Yes | If artifact: file path + location; if clarification: date + question |
| `assumptions` | array[string] | No | List of assumptions if information inferred |
| `priority` | enum | No | "high", "medium", "low" (optional for scoping) |

### Example (Artifact-Sourced Feature)

```markdown
### Feature: User Authentication

**Description**: Users must be able to securely log in using email and password with multi-factor authentication support. Session management includes automatic timeout after 30 minutes of inactivity.

**Source**: [requirements.pdf](solution-artifacts/requirements.pdf) - See page 12, section "Security Requirements"

**Assumptions**:
- OAuth integration for social login deferred to Phase 2
- Password complexity requirements follow NIST SP 800-63B guidelines
```

### Example (Clarification-Sourced Feature)

```markdown
### Feature: API Rate Limiting

**Description**: Public API endpoints must enforce rate limiting to prevent abuse. Standard tier allows 1000 requests per hour per API key.

**Source**: Agent Clarification - 2026-02-03 - Question: "What performance and scalability requirements apply to the API?"

**Assumptions**:
- Premium tier rate limits to be defined based on customer demand
```

### Validation Rules

1. **Mutual Exclusivity**: Feature cannot have both artifact and clarification sources
2. **Completeness**: Every feature must have exactly one source
3. **Description Length**: 1-3 sentences (50-300 characters)
4. **Traceability**: Artifact references must be resolvable file paths in `./solution-artifacts/`
5. **Assumptions Format**: Bulleted list, each assumption is a complete sentence

## 3. Artifact Metadata

**Definition**: Processing state for each input file in `./solution-artifacts/`

**Purpose**: Track progress, report errors, enable traceability

### Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `filename` | string | Original filename (e.g., "requirements.pdf") |
| `file_path` | string | Relative path from project root |
| `file_type` | enum | "pdf", "docx", "txt", "md", "image", "unsupported" |
| `size_bytes` | integer | File size in bytes |
| `processing_status` | enum | "pending", "processing", "success", "failed", "skipped" |
| `error_message` | string? | Error details if status is "failed" or "skipped" |
| `extracted_text_length` | integer? | Character count of extracted text (if successful) |
| `processed_at` | timestamp | ISO 8601 format (YYYY-MM-DDTHH:MM:SSZ) |

### Lifecycle

1. **Discovery**: Scan `./solution-artifacts/`, create metadata entry for each file
2. **Processing**: Update status as each file is processed
3. **Completion**: Final status for all files
4. **Reporting**: Generate summary (X/Y files processed, Z failed)

### Status Transitions

```
pending → processing → success
                   └→ failed
                   └→ skipped (if unsupported or OCR unavailable)
```

### Example

```json
{
  "filename": "architecture-diagram.png",
  "file_path": "./solution-artifacts/architecture-diagram.png",
  "file_type": "image",
  "size_bytes": 245678,
  "processing_status": "skipped",
  "error_message": "OCR capability not available - image file skipped",
  "extracted_text_length": null,
  "processed_at": "2026-02-03T14:32:15Z"
}
```

**Note**: This metadata is ephemeral (in-memory during processing) and not persisted. Only used for progress reporting and error summary.

## 4. Clarification Question

**Definition**: Interactive question-answer pair for gathering missing information

**Lifecycle**: Asked sequentially (1 at a time), answered by user, recorded in spec

### Attributes

| Attribute | Type | Required | Description |
|-----------|------|----------|-------------|
| `question_number` | integer | Yes | 1-5 (max 5 questions per session) |
| `question_text` | string | Yes | The question being asked |
| `category` | enum | Yes | "security", "integration", "data", "performance", "ux" |
| `format` | enum | Yes | "multiple_choice" or "short_answer" |
| `options` | array[Option] | Conditional | Required if format is "multiple_choice" |
| `recommended_option` | string | Conditional | Recommended choice (A/B/C/D) if multiple_choice |
| `suggestion` | string | Conditional | Suggested answer if short_answer format |
| `rationale` | string | Yes | Why this question is being asked |
| `answer` | string | No (until answered) | User's final answer |
| `answered_at` | timestamp | No | When user answered |

### Option Sub-Entity (for Multiple Choice Questions)

| Attribute | Type | Description |
|-----------|------|-------------|
| `letter` | string | A, B, C, D, or "Short" |
| `description` | string | What this option means |
| `implications` | string | Consequences of choosing this option |

### Example (Multiple Choice)

```json
{
  "question_number": 1,
  "question_text": "What authentication approach should the solution use?",
  "category": "security",
  "format": "multiple_choice",
  "options": [
    {
      "letter": "A",
      "description": "Username/password with optional MFA",
      "implications": "Simple to implement, widely understood, requires password management"
    },
    {
      "letter": "B",
      "description": "Single Sign-On (SSO) via SAML or OAuth",
      "implications": "Enterprise-friendly, delegates identity management, requires IdP integration"
    },
    {
      "letter": "C",
      "description": "API key based (for machine-to-machine)",
      "implications": "No user interface needed, suitable for backend integrations only"
    },
    {
      "letter": "Short",
      "description": "Provide a different short answer (≤5 words)",
      "implications": null
    }
  ],
  "recommended_option": "B",
  "rationale": "Enterprise environments typically require SSO integration for centralized access management",
  "answer": "B",
  "answered_at": "2026-02-03T14:35:22Z"
}
```

### Example (Short Answer)

```json
{
  "question_number": 3,
  "question_text": "What is the expected number of concurrent users?",
  "category": "performance",
  "format": "short_answer",
  "suggestion": "100-500 users",
  "rationale": "Helps determine infrastructure sizing and caching strategy",
  "answer": "200 users",
  "answered_at": "2026-02-03T14:36:45Z"
}
```

### Recording in Spec

After each answer, append to spec.md:

```markdown
## Clarifications

### Session 2026-02-03

- Q: What authentication approach should the solution use? → A: Single Sign-On (SSO) via SAML or OAuth
- Q: What is the expected number of concurrent users? → A: 200 users
```

## 5. C4 Diagram Entities

**Definition**: Mermaid code blocks representing system architecture

### C4 Context Diagram

**Purpose**: Show system in its environment (actors, system boundary, external systems)

**Key Elements**:

| Element Type | Mermaid Syntax | Purpose |
|--------------|----------------|---------|
| Person | `Person(alias, "Name", "Description")` | Human actors (users, admins, etc.) |
| External Person | `Person_Ext(alias, "Name", "Description")` | External stakeholders |
| System | `System(alias, "Name", "Description")` | The system being designed |
| External System | `System_Ext(alias, "Name", "Description")` | Third-party or existing systems |
| Boundary | `Enterprise_Boundary(alias, "Label")` | Organizational boundaries |
| Relationship | `Rel(from, to, "Label", "Protocol")` | Interactions between elements |

**Complexity Limits**:
- 3-7 actors
- 5-10 systems
- 1-3 boundaries

**Validation**: Must pass `mermaid-diagram-validator` before inclusion

### C4 Container Diagram

**Purpose**: Show major system components and technologies

**Key Elements**:

| Element Type | Mermaid Syntax | Purpose |
|--------------|----------------|---------|
| Container | `Container(alias, "Name", "Tech", "Description")` | Applications, services |
| Database | `ContainerDb(alias, "Name", "Tech", "Description")` | Data storage |
| Queue | `ContainerQueue(alias, "Name", "Tech", "Description")` | Message queues |
| External Container | `Container_Ext(alias, "Name", "Tech", "Description")` | Third-party components |
| Boundary | `Container_Boundary(alias, "Label")` | Component grouping |

**Complexity Limits**:
- 5-15 containers
- Always include technology (3rd parameter)
- 1-2 boundaries

**Validation**: Must pass `mermaid-diagram-validator` before inclusion

## 6. Processing State (Ephemeral)

**Definition**: In-memory state maintained during imagine command execution

**Purpose**: Track workflow progress, coordinate clarifications with artifact processing

### State Machine

```
INITIALIZING → SCANNING_ARTIFACTS → PROCESSING_ARTIFACTS → 
ASKING_CLARIFICATIONS → GENERATING_DESIGN → VALIDATING → COMPLETE
```

### State Attributes

| State | Description | Transitions |
|-------|-------------|-------------|
| `INITIALIZING` | Setup, check directories, load templates | → SCANNING_ARTIFACTS |
| `SCANNING_ARTIFACTS` | Discover files in ./solution-artifacts/ | → PROCESSING_ARTIFACTS |
| `PROCESSING_ARTIFACTS` | Extract text from files | → ASKING_CLARIFICATIONS |
| `ASKING_CLARIFICATIONS` | Interactive Q&A loop (max 5 questions) | → GENERATING_DESIGN |
| `GENERATING_DESIGN` | Create summary, diagrams, features | → VALIDATING |
| `VALIDATING` | Validate Mermaid syntax, feature sources | → COMPLETE or → GENERATING_DESIGN (retry) |
| `COMPLETE` | Write solution-design.md, report success | (terminal state) |

### Error Handling

- Artifact processing errors: Continue processing, collect errors for summary
- Clarification timeout: Use default/assumption and document
- Diagram validation failure: Fall back to placeholder with TODO notes
- File write failure: Retry once, then abort with error

## 7. Versioning Strategy

**Auto-versioning** (per Q4 clarification): Always create new version without prompting

### Version Determination Logic

```
IF solution-design.md does NOT exist:
  output_file = "solution-design.md"
  version_metadata = "v1"
ELSE:
  Find highest existing version number N in:
    - solution-design.md (v1)
    - solution-design-v2.md
    - solution-design-v3.md
    - ...
  output_file = "solution-design-v{N+1}.md"
  version_metadata = "v{N+1}"
```

### Example Progression

```bash
# First run
/speckit.imagine  →  solution-design.md (version: v1)

# Second run
/speckit.imagine  →  solution-design-v2.md (version: v2)

# Third run
/speckit.imagine  →  solution-design-v3.md (version: v3)
```

**Versioning Scope**: Filenames only. Frontmatter `version` field matches the filename suffix.

## Relationships

```
Solution Design Document (1)
  ├─ contains ─→ Feature Entity (0..N)
  ├─ embeds ─→ C4 Context Diagram (1)
  └─ embeds ─→ C4 Container Diagram (1)

Feature Entity (1)
  ├─ references ─→ Artifact Metadata (0..1)  [if source_type = "artifact"]
  └─ references ─→ Clarification Question (0..1)  [if source_type = "clarification"]

Clarification Question (1..5)
  └─ generates ─→ Feature Entity (0..N)  [answers may inform multiple features]

Artifact Metadata (0..N)
  └─ extracted_for ─→ Feature Entity (0..N)  [one artifact may inform multiple features]
```

---

## Constraints

1. **File-based only**: No databases, all data stored in markdown/JSON files
2. **Human-readable**: All persistent data must be readable/editable by humans
3. **Version control friendly**: Text-based formats (markdown, YAML, Mermaid)
4. **No sensitive data validation**: User responsible for reviewing output (per Q5 clarification)
5. **Idempotent**: Running imagine multiple times creates new versions without destroying previous work
6. **Cross-platform**: All file paths use forward slashes, UTF-8 encoding
